# RAG 구축 방식

## 핵심 요약

이 프로젝트의 RAG는 **문서를 질병·작물·목적 메타데이터와 함께 청크로 만들고, multilingual-e5-base로 정규화 벡터를 구축한 뒤, 사용자가 선택한 작물과 비전 모델의 질병 후보를 조건으로 근거를 검색하는 방식**입니다.

최종 active 인덱스:

| 항목 | 값 |
|---|---:|
| 임베딩 모델 | `intfloat/multilingual-e5-base` |
| 벡터 수 | 38,697 |
| 차원 | 768 |
| 정규화 | L2 normalized |
| 유사도 | cosine similarity (정규화 벡터 내적) |
| 저장 | NumPy `embeddings.npy` + JSONL metadata + manifest |
| 최종 인덱스 엔진 | 별도 벡터 DB 없이 메모리 내 NumPy 검색 |

## 1. 자료 수집

농촌진흥청 농사로, 국가농작물병해충관리시스템(NCPMS), 한국식물병명목록, ADP 계열 농업 자료, 초기 검토 문헌을 수집했습니다. 최종 인덱스의 source group 구성은 다음과 같습니다.

| source group | 청크 수 |
|---|---:|
| ADP | 30,998 |
| 농사로 | 6,723 |
| 한국식물병명목록 | 509 |
| 초기 검토 문헌 | 352 |
| NCPMS | 115 |
| 합계 | **38,697** |

## 2. 정규화와 청킹

수집된 자료의 병명, 작물명, 증상, 발생 조건, 예방/방제, 출처 URL을 공통 필드로 정리했습니다. 문서는 의미 단위로 나누되 지나치게 짧거나 긴 조각을 줄이기 위해 대략 다음 범위를 사용했습니다.

- 목표 길이: 약 850자
- 최대 길이: 약 1,500자
- 최소 길이: 약 60자

각 청크에는 다음 메타데이터를 유지했습니다.

```text
chunk_id
disease_id / disease_name
host / crop
category (symptom, cause, prevention, treatment 등)
source_group
source_title
source_url 또는 원문 식별자
text_hash
```

## 3. 임베딩 문자열

E5 모델의 학습 형식에 맞춰 문서와 질의를 구분했습니다.

```text
passage: disease=<질병> categories=<범주> text=<청크 본문>
query: <사용자 작물 + 질병 후보 + 필요한 정보 목적>
```

`SentenceTransformer`로 배치 임베딩한 뒤 L2 정규화했습니다. 따라서 검색 시 `query_vector @ document_matrix.T`로 cosine similarity와 같은 값을 계산할 수 있습니다.

## 4. 검색 경로

### 모바일 서버 경로

실시간 응답을 위해 단순하고 보수적인 흐름을 사용합니다.

1. 사용자가 선택한 host 확인
2. 분류 모델의 질병 후보 확인
3. host가 일치하는 문서만 후보로 제한
4. 질의를 임베딩하고 cosine top-k 검색
5. 최소 유사도 기준(기본 0.30) 미만 제외
6. 상위 근거(기본 10개)를 LLM 입력으로 전달

### 연구용 하네스 경로

검색 품질을 분석할 때는 더 무거운 파이프라인을 사용했습니다.

1. 증상·원인·발생 조건·방제 등 목적별 다중 질의 생성
2. 질의마다 후보 30개 수집
3. Reciprocal Rank Fusion, `k=60`
4. 상위 20개를 `BAAI/bge-reranker-v2-m3`로 재정렬
5. 같은 출처의 과도한 점유를 막기 위해 출처별 최대 2개 제한
6. 목적별 최종 근거 최대 4개 선택

이 구조는 검색 결과가 한 문서나 한 기관에만 편향되는 것을 줄이고, “증상은 설명되지만 방제 근거가 없는” 상태를 발견하는 데 유리했습니다.

## 5. 근거 기반 생성

LLM에는 원본 이미지 전체를 자유롭게 해석시키지 않고 다음 정보를 전달합니다.

- 사용자가 선택한 작물
- 분할 마스크 통계
- 분류 후보와 확률
- 목적별 RAG 근거
- 각 근거의 출처
- 출력 JSON 스키마와 금지 규칙

1차 출력 후 필수 필드와 인용을 검사합니다. 값이 비었거나 근거가 없으면 해당 목적만 상세 검색하고 누락 필드만 재생성합니다. 이 방식은 전체 답을 매번 다시 생성할 때 생기는 불안정성을 줄입니다.

## 6. 데이터 품질 감사

최종 인덱스를 활성화하기 전에 다음을 검사했습니다.

| 검사 | 최종 결과 |
|---|---:|
| strict pass | true |
| 중복 `chunk_id` | 0 |
| 중복 본문 hash | 0 |
| 메타데이터 불일치 | 0 |

검색 품질은 벡터 점수만으로 평가하지 않았습니다. 실제 답변에서 원문까지 추적 가능한지, 선택 작물과 일치하는지, 필요한 목적별 근거가 있는지를 함께 확인했습니다.

초기 문헌 코퍼스 352개 청크에는 직접 URL이 없었지만 `source`, `source_service`, `source_file` 등 대체 추적 정보가 있어 `all_trace_information` 누락은 0이었습니다. 공개 포트폴리오에서는 이를 숨기지 않고 source audit 원본 요약을 함께 제공합니다.

## 7. RAGAS를 사용했는가?

아니요. `RAGAS` 패키지 기반의 faithfulness/context recall 점수를 사용한 구현은 확인되지 않았습니다. 대신 프로젝트 목적에 맞춘 다음 검사를 사용했습니다.

- 인덱스 중복과 메타데이터 정합성
- 출처 provenance와 URL/원문 추적
- host-aware 검색 제약
- 증상·원인·방제 등 목적별 evidence coverage
- 필수 JSON 필드와 인용 검사
- 원본/환경 증강 이미지 end-to-end 진단 비교

따라서 발표나 면접에서는 “RAGAS로 평가했다”가 아니라 **“RAGAS 대신 진단 위험에 맞춘 출처·작물 정합성·필드 완전성 중심의 맞춤 평가 하네스를 만들었다”**고 설명하는 것이 정확합니다.

## 8. 질문을 받았을 때의 짧은 답변

> 공공 농업 자료를 질병·작물·정보 목적 단위로 정제하고 약 850자 중심으로 청킹했습니다. multilingual-e5-base로 `passage:` 형식의 768차원 정규화 벡터 38,697개를 만들었고, 질의는 `query:` 형식으로 임베딩해 cosine similarity로 검색했습니다. 앱에서는 사용자가 선택한 작물과 분류 후보로 검색 범위를 제한하고, 연구 하네스에서는 다중 질의, RRF, BGE reranker, 출처 다양성 제한까지 적용했습니다. RAGAS 패키지는 쓰지 않았고 출처 추적, host 일치, 중복, 필드 완전성 중심으로 직접 평가했습니다.
