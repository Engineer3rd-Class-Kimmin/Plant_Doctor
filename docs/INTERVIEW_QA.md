# 면접·발표용 질문과 답변

## 프로젝트를 한 문장으로 설명하면?

식물 잎 사진에서 병변 위치를 SegFormer로 찾고, ConvNeXt로 질병 후보를 분류한 뒤, 공공 농업 자료 RAG를 통해 근거가 있는 설명을 제공하는 Flutter 기반 Android 진단 앱입니다.

## 개인적으로 무엇을 담당했나요?

문제 정의, 데이터 조사와 정제, 분할·분류 모델 학습, 환경 증강, 평가 하네스, RAG 수집·정제·임베딩·검색, LLM 검증 흐름, FastAPI 서버, Flutter 앱, 실기기 연동과 발표 정리를 모두 혼자 수행했습니다.

## 왜 한 번에 질병을 분류하지 않았나요?

전체 이미지에는 배경과 정상 잎 조직이 많이 포함됩니다. 먼저 병변을 분할하면 사용자가 판단 위치를 확인할 수 있고, 분류기도 병변 특징에 집중할 수 있습니다. 설명 가능성과 입력 품질을 동시에 개선하기 위한 2단계 구조입니다.

## 왜 사용자가 작물을 먼저 선택하나요?

서로 다른 작물의 질병이 비슷하게 보일 수 있고 사진만으로 작물까지 항상 안정적으로 식별하기 어렵기 때문입니다. 사용자의 작물 선택을 host constraint로 사용해 분류 후보와 RAG 문서를 동시에 제한했습니다. 이것은 UI 편의 기능이 아니라 오진을 줄이는 안전장치입니다.

## RAG 벡터는 어떻게 만들었나요?

공공 농업 자료를 질병·작물·증상·원인·방제 메타데이터와 함께 약 850자 중심으로 청킹했습니다. `multilingual-e5-base`로 `passage:` 형식의 768차원 벡터를 만들고 L2 정규화했습니다. 최종 인덱스는 38,697개 벡터이며, 질의는 `query:` 형식으로 임베딩해 cosine similarity로 검색합니다.

## FAISS나 벡터 DB를 사용했나요?

최종 모바일 서버는 별도 벡터 DB 없이 NumPy 행렬을 메모리에 로드해 정규화 벡터 내적으로 검색합니다. 현재 규모에서는 구조가 단순하고 로딩·배포가 쉬웠습니다. 더 큰 규모나 동적 업데이트가 필요하면 FAISS/Qdrant 같은 엔진으로 교체할 수 있도록 metadata와 index manifest를 분리했습니다.

## RAGAS를 사용했나요?

RAGAS 패키지는 사용하지 않았습니다. 대신 진단 위험에 더 직접적인 출처 추적, 작물 일치, 중복, 메타데이터 정합성, 목적별 근거 커버리지, JSON 필드 완전성을 검사하는 맞춤형 평가 하네스를 만들었습니다.

## RAG에서 가장 중요하게 본 부분은?

유사도 점수보다 provenance와 host 일치를 중요하게 봤습니다. 검색 결과가 그럴듯해도 다른 작물 자료거나 원문 출처를 찾을 수 없으면 진단 근거로 쓰지 않았습니다. 최종 인덱스 감사에서 중복 청크 ID, 중복 본문 해시, 메타데이터 불일치를 모두 0으로 정리했습니다.

## LLM은 어떤 역할을 하나요?

LLM이 이미지에서 병명을 자유롭게 추측하는 구조가 아닙니다. 분할·분류 결과와 검색된 근거를 받아 증상, 원인, 관리 방법을 JSON으로 구성합니다. 이후 인용과 필수 필드를 검사하고 부족한 부분만 재검색·재생성합니다.

## 최종 모델 성능은?

SegFormer-B3는 PlantSeg 원본 테스트에서 Dice 80.26%, IoU 67.03%, Recall 82.65%입니다. ConvNeXt-Small은 best epoch 21에서 Top-1 82.72%, Top-3 93.11%, Macro Recall 81.72%입니다.

## 왜 이전 모델보다 지표가 낮아 보이는 결과도 있나요?

실험마다 모델, 클래스 범위, 데이터 split, host constraint, 원본/증강 테스트가 다릅니다. 예를 들어 host-constrained 정확도는 전체 클래스 정확도와 같은 지표가 아닙니다. 그래서 서로 다른 프로토콜의 숫자를 직접 빼서 개선율로 말하지 않고 각 평가 조건을 함께 제시합니다.

## 클래스 불균형은 어느 정도였나요?

PlantSeg 정규화 386개 클래스 중 273개가 10장 미만, 284개가 30장 미만이었습니다. 이를 완전히 해결했다고 주장하기보다 대상 작물을 24개로 제한하고, 62개 질병 클래스를 구성하며, Macro Recall과 Top-3, host constraint를 사용했습니다.

## 빈 마스크는 몇 건이었나요?

병변 데이터에서 오류로 제외한 빈 마스크는 16건입니다. 별도로 PlantWild 정상 잎 4,000장에는 병변이 없다는 정답으로 빈 마스크 4,000개를 의도적으로 만들었습니다. 두 수치를 합쳐 모두 오류라고 하면 안 됩니다.

## 현장 성능 문제는 어떻게 다뤘나요?

회전, 그림자, 역광, 밝기·감마, 색온도, 블러, 노이즈, 압축을 조합한 증강을 적용했습니다. 정상 잎과 실패 사례도 hard negative로 학습해 배경 오탐을 줄이려 했고, 실제 카메라 입력부터 앱 결과까지 end-to-end로 확인했습니다.

## 가장 어려웠던 점은?

모델 하나의 정확도를 올리는 것보다 데이터 불균형, 정상 잎 오탐, 작물 불일치 검색, 출처 없는 LLM 설명, 모바일 네트워크·환경 의존성을 하나의 제품 흐름에서 동시에 통제하는 것이 가장 어려웠습니다.

## 지금 다시 한다면 무엇을 개선하나요?

실제 농가의 독립 외부 테스트셋과 전문가 검수 Gold set을 먼저 설계하고, 데이터·모델·RAG 인덱스·앱 버전을 하나의 실험 추적 체계로 묶겠습니다. OOD 탐지와 불확실성 보정도 제품 기능으로 포함하겠습니다.
