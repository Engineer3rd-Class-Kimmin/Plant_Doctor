# 개발 과정과 문제 해결

## 1. 시작: “분류 결과”보다 “근거 있는 진단”

처음에는 식물 사진을 분류하는 문제로 시작했지만, 실제 사용자가 원하는 것은 단순한 라벨이 아니었습니다. 어디가 병변인지, 왜 그 질병으로 판단했는지, 무엇을 확인하고 어떻게 관리해야 하는지가 함께 필요했습니다. 그래서 프로젝트를 병변 분할, 질병 분류, 근거 검색, 설명 생성의 네 단계로 분리했습니다.

## 2. 데이터 구조를 먼저 검증

PlantSeg에는 병변 이미지와 마스크가 있었지만 클래스 수가 많고 표본이 매우 불균형했습니다. 정규화한 기준에서 386개 클래스 중 10장 미만 클래스가 273개, 30장 미만이 284개였습니다. 분류 데이터셋을 만드는 과정에서는 병변이 전혀 없는 비정상 빈 마스크 16건을 제외했습니다.

PlantWild의 healthy 이미지는 병변이 없는 정상 잎을 학습하기 위한 hard negative로 사용했습니다. 이 경우 빈 마스크는 오류가 아니라 정상 샘플의 정답입니다. 준비한 4,000장의 healthy 샘플에는 의도적으로 4,000개의 빈 마스크를 생성했습니다. 두 종류의 “빈 마스크”를 같은 데이터 오류로 세지 않은 것이 중요합니다.

## 3. 1차 모델: 병변 검출과 질병 분류의 분리

전체 이미지를 바로 질병 클래스로 분류하면 배경, 화분, 손, 정상 잎 조직이 특징 학습을 방해할 수 있었습니다. SegFormer로 병변 영역을 먼저 구하고, ConvNeXt가 병변 crop을 분류하도록 구조를 분리했습니다. 이 설계 덕분에 앱에서 사용자가 병변 위치를 확인할 수 있고, 분류 입력도 더 명확해졌습니다.

## 4. 실제 촬영 환경에서의 성능 저하

정제된 데이터에서는 잘 동작해도 휴대폰 영상에서는 다음 문제가 나타났습니다.

- 세로/가로 회전과 기기 방향 변화
- 역광과 강한 그림자
- 과노출·저조도
- 초점 흔들림과 모션 블러
- JPEG/영상 압축 노이즈
- 배경을 병변으로 오인하는 false positive

이를 해결하기 위해 단순 좌우 반전뿐 아니라 회전, 밝기·감마·대비, 색온도, 그림자·역광, 블러, 노이즈, 압축을 조합한 대량 증강 파이프라인을 만들었습니다. PlantWild 정상 잎과 실패 사례도 hard negative로 섞어 “병변이 없을 때 0을 출력하는 능력”을 함께 학습했습니다.

## 5. B2/Tiny에서 B3/Small로 확장

초기 SegFormer-B2와 ConvNeXt-Tiny 조합을 기준선으로 삼고, 최종 제품 범위에서는 SegFormer-B3와 ConvNeXt-Small로 확장했습니다. 모델을 키우는 것만이 목표는 아니었습니다. 24개 대상 작물로 범위를 명확히 하고, 분할 마스크 품질, host 제약, 대량 환경 증강, 앱 추론 흐름을 함께 바꿨습니다.

최종 B3는 원본 PlantSeg 평가에서 Dice 80.26%, IoU 67.03%, Recall 82.65%를 기록했습니다. Small 분류기는 epoch 21에서 Top-1 82.72%, Top-3 93.11%, Macro Recall 81.72%를 기록했습니다. 이전 실험과 데이터/평가 조건이 다르므로 숫자를 직접 연결해 “몇 퍼센트 향상”이라고 단정하지 않았습니다.

## 6. RAG: 문서 수집보다 출처 추적을 우선

초기에는 농업 API와 문헌을 모아 질병별 검색 문서를 만들었습니다. 이후 단순히 문서를 늘리는 것보다 다음 품질 문제가 중요하다는 것을 확인했습니다.

- 같은 문장이 여러 출처에서 중복되는 문제
- 병명/작물 메타데이터가 본문과 다른 문제
- 출처 URL이 사라지거나 원문까지 추적되지 않는 문제
- 질병 후보와 다른 작물의 자료가 검색되는 문제
- 증상 근거는 있지만 방제 근거가 없는 문제

그래서 청크 ID·본문 해시 중복 검사, 메타데이터 정합성 검사, 출처 provenance 감사, host filter, 목적별 검색을 추가했습니다. 최종 active 인덱스는 38,697개 벡터이며 감사 결과 중복 청크 ID 0, 중복 해시 0, 메타데이터 불일치 0으로 기록했습니다.

## 7. RAGAS 대신 맞춤 평가를 사용한 이유

이 프로젝트에는 `ragas` 패키지의 표준 점수를 적용하지 않았습니다. 진단 시스템에서 더 직접적인 위험은 “출처 없는 설명”, “다른 작물의 근거”, “필수 관리 정보 누락”이라고 판단했기 때문입니다. 따라서 인덱스 무결성, 출처 추적, host 일치, 목적별 근거 커버리지, JSON 필드 완전성, 원본/증강 이미지 end-to-end 결과를 검사하는 맞춤형 하네스를 만들었습니다.

## 8. 앱 통합에서 발견한 운영 문제

서버와 앱을 연결하면서 모델 성능 외의 운영 문제가 드러났습니다.

- PowerShell 실행 정책으로 `Activate.ps1` 실행 실패
- 시스템 Python에는 `pillow_heif`가 없어 서버 import 실패
- 브라우저에서 서버 루트(`/`)를 열어 404를 서버 장애로 오해
- 휴대폰에서 PC의 `localhost`를 사용할 수 없음
- 모델과 RAG 로딩 시간 동안 요청이 먼저 들어오는 문제

가상환경 활성화 대신 해당 환경의 `python.exe`를 직접 호출했고, `/health`를 준비 상태의 기준으로 삼았습니다. 앱은 실제 PC LAN 주소나 터널 주소를 사용하도록 설정했습니다. HEIF 입력 지원 의존성도 서버 환경에 명시했습니다.

## 9. 최종 결과

최종 결과물은 연구 스크립트에 머물지 않고 다음 흐름이 연결된 Android 프로토타입입니다.

- 작물 선택
- 실시간 카메라 병변 마스크
- 카메라/갤러리 사진 진단
- 질병 후보와 신뢰도 표시
- 근거 기반 증상·원인·관리 설명
- 질병 사전
- 날씨와 농업 가이드
- 다국어 UI

## 10. 가장 중점적으로 판단한 기준

1. **현장 오탐 감소:** 정확도 하나보다 정상 잎·배경 false positive를 함께 봄
2. **작물 정합성:** 사진만으로 작물까지 추측하지 않고 사용자의 host 선택을 안전장치로 사용
3. **근거 추적성:** 답변 문장이 어떤 자료에서 왔는지 확인 가능하게 유지
4. **재현 가능한 지표:** 발표 문구보다 실제 `history.csv`, `best_metrics.json`, 인덱스 manifest를 우선
5. **제품 전체 흐름:** 모델 단품이 아니라 촬영부터 결과 화면까지 실제 연결 상태를 확인
